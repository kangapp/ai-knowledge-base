# 贯穿案例：用 OpenSpec 交付文章收藏

这是与 mattpocock 专题对应的教学案例。需求、设计与验收均为**示例设定**，不表示知识库已经实现收藏功能，也不表示已为该仓库初始化 OpenSpec。

本例假设：单用户知识库，一份服务端收藏状态在不同设备重新加载时保持一致；不做账号、分类或实时推送。OpenSpec 采用本地规划目录与默认 `spec-driven`。

## 1. 从阅读意图到明确边界

初始需求是“把值得以后阅读的文章标记起来”。先使用 explore 读取项目边界，再澄清：

| 问题 | 本例采用的决定 |
| --- | --- |
| 收藏是否改变文章审核状态？ | 不改变，只表达阅读意图 |
| 状态在哪里保存？ | 服务端保存，重新加载时读取 |
| 重复点击收藏怎样处理？ | 保持已收藏，不能反向切换 |
| 取消收藏后筛选结果怎样变化？ | 成功后立即移出收藏筛选结果 |
| 保存失败时怎样显示？ | 保留原状态，显示可重试提示 |
| 一期不做什么？ | 多用户、收藏夹分类、实时同步 |

这些是写 Spec 的输入；存储选型、接口设计和页面数据来源在 design 中说明。涉及已有静态页面时，要确认页面如何读取服务端状态，避免收藏后只能等整站重建才显示。

## 2. 创建 Change 与提案

AI 对话中发起：

```text
/opsx:propose add-article-favorites
```

Codex 对应为 `$openspec-propose add-article-favorites`。下面给出可供审阅的示例产物。

### proposal.md

```markdown
## Why

用户阅读知识库时需要保留后续阅读意图，现有文章审核状态无法表达个人收藏。增加独立的收藏能力，让用户刷新页面或换设备重新访问同一服务后仍能找回已标记的文章。

## What Changes

- 支持收藏和取消收藏已有文章。
- 支持仅查看已收藏文章，取消成功后立即移出筛选结果。
- 保存失败时保留原状态并提示重试。
- 收藏状态与审核状态独立；不增加账号、分类或实时同步。

## Capabilities

### New Capabilities
- `article-favorites`：收藏状态、持久化、筛选及操作反馈。

### Modified Capabilities

无。本例假设尚无对应主规范；实际项目须先核对现有能力。

## Impact

涉及文章状态存储、API 读写、列表交互和相应验证。
遵守既有数据库访问、响应格式和文档写回约定。
```

先用 `openspec list --specs` 检查是否已有对应能力。如果已经存在，就改用它的精确路径并编写 MODIFIED 或 ADDED 要求；不能照抄本例的新能力声明。

## 3. 把需求写成 Delta Spec

### specs/article-favorites/spec.md

```markdown
## Purpose

为知识库文章提供独立于审核流程的后续阅读标记，使用户能够保存值得再次查看的内容，在刷新页面或重新访问同一服务后恢复收藏状态，并集中浏览当前收藏的文章。

## ADDED Requirements

### Requirement: 设置收藏状态
系统 SHALL 将已有文章设置为用户明确请求的收藏状态。

#### Scenario: 收藏文章
- **GIVEN** 文章 A 存在且未收藏
- **WHEN** 用户成功请求将 A 设置为已收藏
- **THEN** A 显示为已收藏

#### Scenario: 重复收藏
- **GIVEN** 文章 A 已收藏
- **WHEN** 用户再次成功请求将 A 设置为已收藏
- **THEN** A 仍为已收藏

#### Scenario: 取消收藏
- **GIVEN** 文章 A 已收藏
- **WHEN** 用户成功请求将 A 设置为未收藏
- **THEN** A 显示为未收藏

### Requirement: 持久化收藏状态
系统 SHALL 在重新加载同一服务的文章列表时恢复已保存的收藏状态。

#### Scenario: 刷新与重新访问
- **GIVEN** 文章 A 的收藏状态已保存到服务端
- **WHEN** 用户刷新页面或从另一设备重新加载文章列表
- **THEN** A 显示与服务端已保存状态一致的收藏状态

### Requirement: 筛选收藏文章
系统 SHALL 在收藏筛选模式中仅展示当前已收藏的文章。

#### Scenario: 进入收藏筛选
- **GIVEN** A 已收藏且 B 未收藏
- **WHEN** 用户启用收藏筛选
- **THEN** 结果包含 A 且不包含 B

#### Scenario: 在筛选结果中取消收藏
- **GIVEN** 用户正在收藏筛选中查看文章 A
- **WHEN** A 的取消收藏请求成功
- **THEN** A 立即从当前筛选结果移除

### Requirement: 收藏不改变审核状态
系统 SHALL 在收藏或取消收藏时保留文章的审核状态。

#### Scenario: 审核状态保持不变
- **GIVEN** 文章 A 处于任一既有审核状态
- **WHEN** 用户成功改变 A 的收藏状态
- **THEN** A 的审核状态保持原值

### Requirement: 保存失败反馈
系统 SHALL 在收藏状态保存失败时保留操作前的显示状态并提示用户重试。

#### Scenario: 服务暂时不可用
- **GIVEN** 文章 A 未收藏
- **WHEN** 收藏请求因服务不可用而失败
- **THEN** A 仍显示未收藏，页面出现可重试提示
```

这份示例包含 5 个要求、8 个场景。重复收藏用“设置状态”表达，避免把网络重试当成再次切换。Spec 描述结果，不规定具体函数名或数据库列。

## 4. 把方案取舍留在设计中

### design.md

```markdown
## Context

参见 proposal.md 的动机和范围。系统已有 SQLite、API 与静态页面，
本功能需要在服务端持久化状态，并在页面加载时读取最新状态。

## Goals / Non-Goals

保持收藏读写与既有文章数据访问方式一致。
不通过周期性的整站重建传播每次收藏操作。

## Decisions

- 沿用 SQLite 保存收藏状态，迁移需给既有文章提供未收藏默认值。
  浏览器本地存储无法满足换设备重新加载后的状态一致，因此不采用。
- 写入操作设置目标布尔状态，不使用反转命令，避免重试反转结果。
- API 返回可供页面确认的保存结果；数据库访问与响应结构遵守项目规则。
- 页面初次加载读取服务端状态，保存成功后更新当前显示与筛选结果。
- 保存失败时保留旧显示状态并提供重试入口。

## Risks / Trade-offs

- 静态页面内容可能较旧 → 加载时向 API 读取收藏状态。
- 并发请求可能覆盖状态 → 单用户场景采用最后成功写入的状态，
  前端对同一文章的待完成操作作约束，具体接口验证纳入任务。
- 部署和数据迁移失败 → 先备份数据，复用项目迁移方式，
  发布前确认旧版本可忽略新增状态并给出回退步骤。

## Migration Plan

1. 按既有迁移机制增加存储并验证旧数据兼容。
2. 发布 API 与页面，执行一次收藏、刷新、筛选和取消操作。
3. 若发布失败，按已验证的回退步骤恢复旧版本。
```

本例涉及持久化、API 和页面数据流，保留一份简短 design 有价值；不必把所有函数实现提前写进去。实际执行前还应将这里的方案与真实代码核对。

## 5. 每个任务都带验证方式

### tasks.md

```markdown
## 1. 收藏与取消

- [ ] 1.1 完成持久化与状态设置 API；验证收藏、重复收藏、取消、刷新读取及审核状态不变，并验证旧数据迁移后默认未收藏。
- [ ] 1.2 接入页面按钮与加载时状态读取；用浏览器验证刷新和另一设备重新加载后的状态一致。

## 2. 收藏筛选与失败反馈

- [ ] 2.1 完成收藏筛选；验证只显示已收藏文章，以及取消成功后立即移出结果。
- [ ] 2.2 完成保存失败反馈与请求中的交互约束；模拟请求失败和连续点击，验证旧状态保留、重试提示与最终显示正确。

## 3. 整体验收

- [ ] 3.1 对照全部 8 个场景执行测试和人工验收，记录证据并通过项目要求的检查。
- [ ] 3.2 更新相关 API 与数据模型文档，审阅发布及回退步骤，验证描述与实现一致。
```

这是教学任务划分，真实项目可进一步拆成会话内可完成的小项。验收证据可以引用测试命令、实际结果和 PR，不要求复制全部日志。

与 mattpocock 的纵向 Ticket 相比，OpenSpec 默认把进度集中在这一份文件中。本例没有同时生成两套 Issue 清单；如需远程分工，再明确任务与 Issue 的映射。

## 6. 结构验证、实施与审查

终端先验证文档：

```bash
openspec validate add-article-favorites --type change --strict
openspec status --change add-article-favorites
```

审阅计划后发起 `/opsx:apply add-article-favorites`。如果希望使用 TDD，可在实施约定中说明，让每个测试期望来自上面的行为场景。OpenSpec 本身没有强制“先红后绿”。

测试至少覆盖状态设置的幂等性、持久化、审核状态隔离、筛选结果和失败反馈。完成时核对：

| 验收证据 | 它证明什么 |
| --- | --- |
| CLI validate 成功 | 示例的文档结构与规则成立 |
| API 与持久化测试 | 收藏状态按约定读写 |
| 浏览器场景 | 页面显示、筛选和失败反馈符合约定 |
| 可选 verify 报告 | AI 对照产物找过遗漏与矛盾 |
| 发布后的真实操作 | 已部署版本具备预期行为 |

本专题对示例做结构与归档演练，不实施收藏业务代码；因此没有将示例任务勾选，也不声称产品测试或发布验收已经通过。

**核对结果（2026-09-13）：** 已在临时目录用官方 v1.13.0 CLI 对上述产物严格校验，再演练归档并校验生成的主规范；5 个要求、8 个场景完整保留。演练中未勾选的 6 个任务仍被保留，后续 `validate --archived` 会拒绝这份未完成归档，说明“归档成功”和“任务完成”确实是两个判断。

## 7. 实施中改变需求

假如用户改为“取消收藏后，当前列表暂时保留到刷新”，这不是简单的 UI 实现选择，它改变了一个场景的结果。

发起 `/opsx:update add-article-favorites`：先修订 Delta 中相应 Scenario，再检查提案、设计和任务是否需要调整。对已勾选但不再满足新要求的任务，显式重新打开或增加新任务，再 apply。

不要只改代码留下旧场景，也不要在主规范尚不存在时写一份找不到目标的 MODIFIED。

## 8. 同步并归档

当实现与验收真正完成后，发起：

```text
/opsx:archive add-article-favorites
```

选择同步后，新增能力成为：

```text
openspec/specs/article-favorites/spec.md
  ├─ Purpose
  └─ Requirements：收藏、持久化、筛选、审核隔离、失败反馈

openspec/changes/archive/YYYY-MM-DD-add-article-favorites/
  ├─ .openspec.yaml
  ├─ proposal.md
  ├─ specs/article-favorites/spec.md
  ├─ design.md
  └─ tasks.md
```

主规范中的节标题使用 `## Requirements`；归档里保留原来表示“本次新增”的 `## ADDED Requirements`。下一次修改收藏规则时，读取主规范，复制要改变的完整 Requirement 后写入新的 MODIFIED Delta，保留不受影响的场景。

## 9. 从同一个案例看两种方法

我的理解是：mattpocock 让澄清、测试和审查更有章法；OpenSpec 让需求变化拥有明确的文件生命周期。前者的 Spec Issue 与后者的主规范不完全等价：Issue 往往面向一次交付，主规范需要持续表达当前约定。

本例最有价值的结果不是生成了几份 Markdown，而是下一次做收藏分类或删除文章时，能准确知道既有收藏行为、当初的选择理由和验证证据。

案例格式依据[默认 Schema](https://github.com/Fission-AI/OpenSpec/blob/9d4e5974e5c0d9a09b9c6c1e1eb0975e80ec4461/schemas/spec-driven/schema.yaml)与[规范编写指南](https://github.com/Fission-AI/OpenSpec/blob/9d4e5974e5c0d9a09b9c6c1e1eb0975e80ec4461/docs/writing-specs.md)。对照阅读：[mattpocock 文章收藏案例](/analysis/mattpocock-skills/examples/article-favorites.html)。
