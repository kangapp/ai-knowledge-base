# Prompt 工具箱：按当前阶段选用

这是按需参考。首次使用只需在[开始共创](README.md)复制启动提示词，由 AI 按五步流程推进；某一环节需要更精确控制时，再选用本页模板。

将花括号中的内容替换成你的任务信息，一次选择当前需要的模板。模板规定本轮交付物；业务事实仍需来自材料和人的确认。

这些模板是本指南的实践整理。其基础是明确指令、相关上下文和输出结构；对于推理模型，先保持简洁直接，需要时再补充与任务一致的示例。[官方提示工程指南](https://developers.openai.com/api/docs/guides/prompt-engineering)、[推理模型提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

## P01 · 启动任务与建立共识

适合只有原始材料、尚未确定文档结构时使用。期望得到任务说明与关键缺口。

```text
我们要共创《{文档名称}》。
文档类型：{需求设计 / 实现设计 / 业务逻辑 / 现状说明}
读者与用途：{谁需要用它作出什么决定或完成什么行动}
原始想法：{内容}
已有材料与来源：{内容}
已确认约束与非目标：{内容}

请先形成任务说明：目标、范围、读者、成功标准、材料来源。
区分已确认事实、暂定假设、建议和待定问题。
每轮只提出一个最影响方向的问题，给出 2—3 个选项及其影响。
本轮不展开全文；事实不足处不要自行补齐为已确认内容。
```

检查：AI 是否复述了真实用途，是否把自己的建议混入目标？用途清楚后，再进入澄清或大纲阶段。

## P02 · 把模糊需求变成可回答的问题

适合目标大致清楚，但范围、核心行为或约束还不明确时使用。

```text
当前需求：{内容}
已确认信息与决定：{内容}
可查证的材料：{来源}

请优先处理会改变目标、范围、成本或核心规则的未知项。
本轮只提出一个主要问题，包含具体情境、2—3 个选项及影响、
推荐项和适用前提。允许我自定义答案或暂时保留问题。
能查证的信息先查证，不重复询问已确认事项。
不要把我的沉默当成选择。
列出可以继续的工作，以及必须等待答案的部分。
```

检查：问题是否具体、可回答、与当前阶段相关？答案返回后，更新任务说明和决定记录。

## P03 · 将材料整理为事实与冲突清单

适合聊天记录、旧文档和代码材料较多时使用。

```text
本轮只整理 {主题范围} 的材料。
材料及时间、来源：{内容}
文档用途：{描述现状 / 设计未来行为}

请提取：已确认事实、约束、关键术语、暂定假设、待定问题。
每条关键事实关联来源；区分业务政策、代码现状与设计提议。
如来源冲突，逐项列出差异、适用时间和影响，不自行融合为新事实。
输出简洁表格，并指出下一轮最需要补充的证据。
```

检查：来源是否真的支持结论？AI 没有读取权限的材料，应标记未核实并请人提供相关摘录。

## P04 · 设计主线与章节职责

适合已经形成关键共识、准备组织文档时使用。

```text
任务说明：{内容}
已确认事实、规则与决定：{内容}
目标篇幅和读者背景：{约束}

先写一句话主线，再设计最小必要大纲。
对每章列出：读者问题、核心结论、所需材料、与其他章节的边界。
检查遗漏、重复、抽象层级不一致和先用后定义的问题。
说明哪些信息应放在表格或图中，以及图表要回答什么问题。
输出大纲与需要人决定的结构分歧，本轮不写正文。
```

检查：每一章是否都支持主线？目录能否引导读者从问题走到行动与验证？

## P05 · 分段撰写正文

适合大纲已经可用，需要逐节完成正文时使用。

```text
本轮章节：{章节名称}
章节职责：{要回答的读者问题}
已确认依据：{事实、规则、来源}
全文术语与约束：{内容}
前后章节负责：{摘要}

只写这一节。先给核心结论，再解释条件、行为、结果、例外和必要示例。
每个自然段围绕一个中心意思，段落之间有清楚的关系。
并列比较用表格，连续解释用自然段；避免重复相邻章节。
新发现的事实缺口和决策问题单列，不自行编造业务规则或数值。
```

检查：本节是否可以独立理解，并且与全文一致？若出现新决定，先记录再处理。

## P06 · 改写混乱或空泛的段落

适合已有内容，但表述抽象、重复或层次混杂时使用。

```text
目标读者：{读者}
目标段落：{内容}
必须保留的事实与约定：{内容}
可选风格示例：{仅供表达参考的片段}

先指出影响理解的歧义、重复或信息缺口，再给出改写。
按中心意思拆分自然段，让条件、动作、结果和边界明确。
保留原有事实，不引入新功能、字段、指标或承诺。
示例只用于学习表达方式，不迁移其中的业务规则。
事实不足处保留待补充标记，并简要说明改写理由。
```

检查：改写有没有改变原意？删掉冗余后是否仍保留关键条件？

## P07 · 从业务材料提取规则

适合整理条件分支、对象状态和例外情况时使用。

```text
业务范围与用途：{内容}
业务材料、现有规则与来源：{内容}

先统一术语、对象和状态，再提取事件、条件、动作、结果、例外。
为规则编号并注明来源，区分已确认规则与待确认推断。
检查条件覆盖、规则冲突、优先级和不合法状态变化。
用决策表说明条件组合，用状态图说明合法变化。
提供正常、异常和边界案例；未定义的结果列为待定，不自行决定。
```

检查：仅根据规则表，是否能判断每个案例的结果？状态图是否遗漏重要事件？

## P08 · 根据需求形成实现设计

适合已有需求和代码上下文，需要形成可实施方案时使用。

```text
已确认需求与规则：{编号、正文或链接}
现有架构、代码、接口与数据材料：{内容}
技术约束：{内容}

先概括可核实的现状，再提出满足需求的最小可行设计。
每项主要改动关联需求编号，说明模块职责、接口输入输出和数据约束。
按真实需要讨论重复请求、失败恢复、并发、兼容性与发布安排。
仅比较有实际取舍的方案。拟议名称与结构标为设计建议。
输出设计与验证计划；本轮不实施，不声称未执行的检查已经通过。
```

检查：方案是否符合现有项目模式？每项新增机制是否都有真实需求依据？

## P09 · 生成并核对图表

适合正文已有明确关系，需要辅助解释时使用。

```text
请根据以下已确认正文生成 {流程图 / 时序图 / 状态图 / 决策表}。
正文：{内容}
这张图需要回答：{一个主要问题}

保持对象、术语、状态和分支条件与正文一致，不新增规则。
只包含理解这个问题必需的关系，必要时拆成局部图。
输出 Mermaid 源码或 Markdown 表格，并提供文字解释和图注。
核对成功、失败、例外和返回路径；图中省略的范围在图注说明。
最后列出发现的正文缺口。
```

检查：图是否真的帮助回答问题？发布前实际渲染，核对节点文字、连线和窄屏可读性。

## P10 · 审校内容、逻辑与表达

适合章节完成或全文准备交付时使用。

```text
任务说明、事实来源与约束：{内容}
待审查文档：{内容}

先检查范围与需求覆盖、事实依据、规则冲突、异常边界和可验证性；
再检查主题聚焦、章节职责、段落关系、术语与图文一致性。
每项问题输出：位置、原文或证据、影响、最小修改建议。
无法确认的问题标为待核实，区分阻塞交付与后续改进项。
不要为了增加问题数量而提出范围外功能，不给没有依据的精确评分。
本轮只输出审校清单，不重写全文。
```

检查：每条问题是否真实存在并影响用途？审校建议应接受证据核实，不能自动替代业务决定。

## P11 · 生成验收案例与追踪关系

适合需求规则已明确，需要建立可检查的完成标准时使用。

```text
需求与业务规则：{编号与内容}
范围、约束和待定事项：{内容}

为核心行为设计正常、异常和边界案例。
每个案例包含编号、关联需求、前置条件、操作、预期结果、验证方式。
检查是否存在未被覆盖的需求或没有需求依据的案例。
若预期结果无法从文档确定，列出缺口，不替我决定业务规则。
本轮产出验收计划，全部标为待执行，不生成虚构的执行结果。
```

检查：案例能否被真正执行？性能指标是否具备明确测量条件与已确认阈值？

## P12 · 限定范围进行修订

适合已确认某项变化，需要同步文档时使用。

```text
已确认变更：{旧约定 → 新约定及理由}
当前文档与关联材料：{内容}
本次允许修改的范围：{内容}

先列出受影响的正文、图表、接口、数据与验收案例及原因。
完成必要修订，保留无关内容与原有文风。
检查是否残留旧规则，以及变更是否引出新的冲突或待定问题。
最后报告修改位置、验证结果和遗留事项。
如果影响超出已确认范围，列出扩展影响并等待关键决定。
```

检查：修改是否完整覆盖依赖，同时避免顺手扩写？

## P13 · 交接给下一轮对话

适合长对话接续、换会话或交给其他协作者时使用。

```text
请根据当前文档和已确认讨论生成简洁交接摘要：
目标与范围、当前版本、已确认决定及依据、统一术语、材料入口，
待定事项及影响、已完成和待执行的检查、下一轮任务。
事实、假设、建议分别记录，不把历史提议写成当前决定。
指出历史讨论与当前文档的冲突，保留来源供下一轮核实。
不要复制整段对话，只保留接续工作必需的信息。
```

检查：新协作者能否找到当前版本，并辨别哪些内容仍未确定？

## 常见低效提示与修正

| 低效提示 | 问题 | 修正方向 |
| --- | --- | --- |
| 帮我写一份专业、完整的文档 | 读者、用途和合格标准缺失 | 给任务说明与具体产物 |
| 越详细越好 | 容易引入范围外内容 | 规定章节职责和必要深度 |
| 不清楚就一直问我 | 可能无限提问或重复确认 | 优先高影响问题，明确继续条件 |
| 按最佳实践自行补齐 | 可能把建议写成业务事实 | 列选项和影响，保留待定状态 |
| 自评到满分再输出 | 分数可能没有可核实依据 | 按案例、证据和检查标准审校 |
| 把全文润色一下 | 可能改变约定或扩散修改 | 指定位置、事实保留要求和影响核对 |

## 怎么判断模板需要调整

观察输出中的实际问题，再修改对应指令。缺事实就补材料，结构混乱就补章节职责，术语漂移就提供术语表，验收模糊就要求条件、动作和预期结果。每次保留一个代表性输入，对照修改前后的输出检查效果。

这种按任务持续检查并结合人工判断的做法，借鉴了 [OpenAI 的评估建议](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。不要把单次输出看起来更流畅，直接等同于内容更准确。
