# 场景指南：共同流程，不同关注点

三类文档都按“对齐目标 → 确认全景 → 演示场景 → 完善全文 → 审校定稿”推进。选择类型后，先让读者看到完整逻辑，再补充必要细节。

| 文档类型 | 主要回答什么 | 全景应包含什么 |
| --- | --- | --- |
| 需求设计 | 做什么，用户会得到什么？ | 问题、范围、核心行为、失败反馈、验收 |
| 实现设计 | 怎样满足已确认要求？ | 需求摘要、现状约束、方案、交互、验证 |
| 业务逻辑 | 哪些条件决定什么结果？ | 术语、对象、事件、规则、状态与案例 |

材料与其他文档可以提供来源，但本篇应写明必要定义、核心规则和适用边界。多份文档交付时，各自的行为摘要必须随同一组规则更新。

## 需求设计

先识别用户问题和场景，区分目标与解决方式。“增加收藏按钮”可能服务于稍后阅读，也可能服务于整理资料；这会改变范围和行为，应先澄清。

**全景先确认**：目标使用者、本期范围、主流程、成功与失败结果、关键边界和验收方法。用 HTML 比较行为，用正常例和反例检查理解。

**细节再组织**：背景与目标 → 范围 → 场景与规则 → 验收与待定。技术方案不能替代尚未明确的需求。

```text
依据 {想法与材料} 共创需求设计，读者是 {读者}。
先给简短完整全景，标记未知项；优先澄清最影响方向的问题。
用具体场景展示条件、操作、结果和失败反馈，经确认后维护规则表。
按场景完善整份草稿与验收，必要规则写入正文，不只链接外部文档。
不凭空添加功能或效果指标，默认只展示本轮变化与一个待决定问题。
```

**合格标准**：不同实施者能得出一致的用户行为；验收者能构造具体案例。业务效果指标需要数据来源、基线与观察窗口，没有依据时保持待定。

## 实现设计

先核实当前代码、接口和数据约束。拟议模块与字段标为设计建议，读取代码不等于测试通过。

**全景先确认**：必要需求摘要、相关现状、最小可行方案、职责与主交互、主要失败路径和验证计划。只比较真正有取舍的方案。

**细节再组织**：目标与现状 → 方案 → 模块与接口 → 数据与失败处理 → 实施与验证。发布、迁移和回退仅在本次变更需要时加入。

```text
依据 {已确认需求} 与 {代码材料} 共创实现设计。
先将必要需求和约束写入本篇，再附来源，不用引用代替行为定义。
给出最小方案全景，每项改动对应规则编号；用时序图说明成功与失败。
按实际需要明确重试、并发和兼容性，不增加没有需求依据的新机制。
修改需求时同步设计、图表与验收；未执行的测试保持待执行。
```

**合格标准**：主要选择能追溯到需求或约束；输入、输出、状态与错误行为明确；正常、异常与必要边界有对应验证。

## 业务逻辑说明

先确认描述现状还是设计未来。口述、旧需求和代码分支可能相互冲突，不能自动融合为业务政策。

**全景先确认**：术语、对象与状态、主要事件、关键条件、规则优先级、默认行为和例外。用案例与决策表检查能否确定结果。

**细节再组织**：范围与定义 → 对象 → 事件与流程 → 条件和规则 → 状态与案例 → 来源及未决事项。

```text
依据 {材料} 梳理 {业务范围}，用途是 {描述现状 / 设计未来}。
先给术语、对象、事件、规则与结果的全景，区分政策、现状和推断。
为核心规则编号，明确条件、动作、结果、优先级与例外。
用决策表和状态图检查正常、异常与边界案例，未定义结果列为待定。
必要定义和规则在本篇展开；修改规则后同步全文、图表与案例。
```

**合格标准**：给定一个具体案例，读者能确定结果；未覆盖条件明确标记；状态图与规则表相符，没有隐含优先级。
