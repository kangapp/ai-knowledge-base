# 结构与写作：让文档围绕主题展开

这是按需参考。先从[开始共创](README.md)进入五步流程，正文组织与常规审校由 AI 推进；需要进一步调整表达时再查看本页。

一份结构清楚的 Spec，会让读者先理解问题，再理解行为与约束，最后知道如何行动和验证。标题、自然段、表格和图表都服务于这个阅读顺序。

本页的方法属于写作实践建议。提示中明确任务、上下文和输出格式的原则，参考 [OpenAI Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)。

## 先写一句话主线

一句话主线同时包含主题、读者和用途。例如：“本文为研发和测试约定个人知识库收藏功能的范围、行为与验收方式，使不同实现者对结果有一致理解。”

每写完一节，都检查它与主线的关系。背景只保留会影响当前决定的信息；扩展想法列为后续方向或移除。关于收藏功能的需求文档，没有必要展开推荐算法、社交分享和完整账户体系。

```text
请用一句话概括本文的主题、目标读者和用途。
逐节说明它怎样支持这句话，并标出：偏离主题、重复、缺少前置说明的内容。
给出最小结构调整建议，保留已经确认的业务事实。
```

## 用读者问题确定章节顺序

| 读者当前的问题 | 章节职责 | 不应混入的内容 |
| --- | --- | --- |
| 为什么需要这个变化？ | 说明背景、问题与目标 | 提前堆砌技术实现细节 |
| 这次解决到哪里？ | 定义范围、角色、约束与非目标 | 尚未承诺的未来功能 |
| 在具体情况下会怎样？ | 说明场景、行为、规则与例外 | 无关架构历史 |
| 如何落实这些约定？ | 在实现设计中解释方案与职责 | 再次定义不同版本的业务规则 |
| 怎样知道完成了？ | 给出验收场景和验证方式 | “体验良好”等不可判定结论 |

这是一种常用顺序，实际可按文档用途调整。排障说明可以先写症状和定位步骤；业务规则说明可以先定义术语与对象，再讲条件和状态。

大纲中的标题要能预测内容。例如，“收藏操作的持久化与失败反馈”比“其他说明”更具体。同级标题尽量处于同一层级，不把“业务目标”“数据库字段”“测试一下”混成三个并列章节。

## 为每章写一份内容约定

正式展开前，可以在草稿里为章节写一段说明：

```text
章节：取消收藏
要回答的问题：从不同入口取消收藏后，用户看到什么？
必须包含：触发条件、状态变化、列表反馈、失败反馈、重复操作。
依据：已确认规则 R-03、R-04。
不在本节展开：数据库结构、接口实现、未来批量操作。
与前后文的关系：引用收藏定义；验收章节提供对应案例。
```

这段约定是共创过程的中间产物，交付正文不必保留全部写作说明。它的作用是控制本轮范围，并让 AI 知道哪些内容已经在别处负责。

## 一个自然段推进一个中心意思

自然段可以从结论或行为开始，再补适用条件、依据和必要例子。一个段落承载两个独立规则时，通常应拆开；一句话就已表达完整的内容，也不必为了统一格式强行扩写。

下面是教学案例中的改写。规则均为示例假设。

**原始段落**

> 收藏功能需要方便易用，用户能快速管理收藏，系统应智能处理异常，保证数据一致性，也要考虑将来的扩展。

**改写后的段落**

> 用户可以在文章列表中收藏文章。保存成功后，按钮显示“已收藏”；刷新页面后仍保留该状态。

> 用户在收藏列表中取消收藏时，保存成功后该文章从当前列表移除。取消操作只删除收藏关系，不删除文章本身。

> 保存失败时，页面保留操作前的已确认状态，并显示失败提示与重试入口。界面不将未保存的结果显示为已完成。

改写后，三段分别说明新增、取消和失败行为。正文中的“成功后”给出了状态变化的条件，“不删除文章”限定了影响范围，读者能够据此设计检查案例。

## 把模糊词换成可判定的约定

| 模糊表达 | 应补充的问题 | 可采用的表达 |
| --- | --- | --- |
| 快速返回 | 测量条件与目标是什么？ | 明确负载、分位值与阈值；没定就标为待定 |
| 支持重复操作 | 重复后的状态、数量和时间如何变化？ | 同一文章保留一条收藏；重复收藏不更新时间 |
| 合理处理异常 | 哪些失败能恢复？用户看到什么？ | 保存失败保留原状态，并提供重试入口 |
| 保证一致性 | 哪些入口或数据必须一致？何时一致？ | 刷新后从服务器读取已确认的收藏状态 |
| 易于扩展 | 本期存在什么明确变化需求？ | 写已知约束；没有需求时不增加扩展结构 |

不要为了“可量化”而凭空填写响应时间、准确率或并发指标。缺少目标和测试条件时，先将它们列为待定事项。

## 用实例和反例界定规则

写出规则后，增加一个正常例和一个容易误读的反例。例如：“取消收藏只移除收藏关系”可以配合“文章仍在全部文章列表中”的正常结果，以及“不能因此删除文章记录”的边界说明。

给 AI 提供风格示例时，明确哪些部分用于学习表达，哪些属于真实业务规则。否则模型可能将示例中的字段名、数字或功能一起迁移到新文档中。示例应与当前指令一致；对于推理模型，可以先使用直接要求，效果不足时再补示例。[官方示例使用建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices#how-to-prompt-reasoning-models-effectively)

```text
请参照下面示例的表达方式改写目标段落。
仅学习“行为 → 条件 → 结果 → 边界”的组织方式，
不要引入示例中的业务规则、数据、字段名或性能指标。
保留目标段落全部已确认事实；事实不足处标记为待补充。
```

## 统一术语并连接章节

先建立少量必要定义。例如：“收藏关系”表示文章与个人收藏清单的关联；“收藏列表”表示仅展示已收藏文章的视图；“取消收藏”表示删除该关联。定义后避免交替使用“书签”“喜欢”“订阅”表达同一行为。

章节之间用内容关系衔接。例如，“上节确定取消收藏后立即移出当前列表，本节据此定义接口成功与失败时的页面反馈。”这样的过渡说明了依赖，也帮助发现前后是否使用同一规则。

当文档拆成多页时，关键规则在一个位置维护，其他页面引用编号或链接。跨页链接应指向读者正在寻找的内容，避免只写“见上文”。

## 选择真正有解释作用的图表

| 需要表达的关系 | 推荐形式 | 检查重点 |
| --- | --- | --- |
| 步骤先后、条件分支与回退 | 流程图 | 分支条件明确，有结束或返回路径 |
| 多方调用、返回和失败顺序 | 时序图 | 参与者、成功与失败交互一致 |
| 对象可处于哪些状态 | 状态图 | 合法变化、触发条件、失败时状态 |
| 多个条件决定不同动作 | 决策表 | 条件组合覆盖，优先级无冲突 |
| 模块职责与依赖 | 架构图 | 边界清楚，箭头含义明确 |
| 对象关系与字段约束 | ER 图或数据字典 | 基数、唯一性、可空性有依据 |
| 选项取舍或需求追踪 | 对照表、对应表 | 比较维度统一，结论有证据 |

一张图解释一个主要问题。正文先说明读者要观察什么，图注再说明适用范围或省略项。流程、时序和状态图可以用 Mermaid 维护；复杂图拆成几张局部图，并保留文字规则，方便读者在图表无法渲染时理解。

对没有数据的定性关系，使用表格即可。不要虚构百分比来画饼图或雷达图，也不要把没有可比尺度的“完整性”“专业度”包装成精确统计结果。

## 局部修订后做一次全文核对

限定修改范围能减少意外改变，但局部改动仍可能影响全文。先让 AI 列出受影响的位置，再修改必要部分，最后检查术语、链接、图表和验收案例。

```text
本次将规则 {原规则} 修改为 {新规则}，已得到确认。
先列出受影响的正文、图表、字段说明与验收案例及原因。
只修改这些位置，保留无关内容和原有文风。
完成后报告实际改动与仍需决定的问题，检查是否遗留旧规则。
```

## 交付前的表达检查

- 标题能够预测内容，同级标题抽象层级一致。
- 每个自然段有明确中心，段落之间具有顺序、因果或依赖关系。
- 必须、可以、建议、待定分别表达约束、许可、提议和未决状态。
- 关键行为有条件、结果和例外，抽象词已被解释。
- 正文、示例与图表使用同一组术语和规则。
- 不保留写作过程中的占位内容，必要未知项有显式标记和影响说明。
