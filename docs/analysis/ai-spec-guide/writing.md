# 结构与写作：自洽、简明、展示一致

写作服务于判断和实施：读者应能在本篇内理解必要概念，根据具体条件确定结果，找到对应验收。先确认需求全景，再组织章节。

## 必要结论写入文档

外部材料提供证据和背景，正文承担解释责任。引用规范时，写明本次采用的具体规则、适用条件与例外，再附来源。无需复制整份规范。

| 依赖外部材料的表达 | 文内能够理解的表达 |
| --- | --- |
| 收藏行为遵循项目一致性规范 | 保存成功后显示已收藏；确认保存失败时保留原状态；结果未知时提示待确认并重新读取服务器状态 |
| 权限沿用现有机制 | 写明本次适用的角色、允许的操作和拒绝行为，再附权限规范来源 |
| 排序见其他文档 | 列表按收藏时间倒序；时间相同则按文章 ID 倒序 |

**检查方法**：暂时忽略外部链接，仅根据本篇解释核心场景。缺少定义、条件或结果时，将必要内容补入正文；无法核实的事实标为待核实，不擅自填补。

一份 Spec 可以分成多个页面，但交付时应包含所需页面。每页给出理解当前内容所需的短定义和规则摘要，链接指向详细规则。核心规则在一处维护，摘要随关联修订更新，避免出现多个手工维护的规则版本。

## 区分来源与决定

| 类型 | 写法 |
| --- | --- |
| 已核实事实 | 陈述内容，注明来源、适用版本或时间 |
| 已确认设计 | 陈述本次约定，关联决定或规则编号 |
| 假设 | 显式标记，说明不成立时的影响 |
| 建议 | 给出适用前提与取舍，不写成强制要求 |
| 待定问题 | 写明缺口、影响和是否阻塞继续 |

代码现状不等于业务政策，旧 Spec 不等于新需求。冲突时分别列出原约定、现状和本次提议，明确哪一项需要人作决定。

## 借鉴 ASD-STE100 的简明表达

[ASD-STE100](https://www.asd-ste100.org/about.html) 是英语受控写作规范，包含写作规则和受控词汇。本指南借鉴其表达原则用于中文，不机械套用英语词数限制，也不宣称中文文档严格符合 STE。

- 一句话表达一个主要意思，一段围绕一个主题。
- 明确执行者，用“服务器保存收藏关系”代替含糊的“进行相关处理”。
- 先写条件，再写动作与结果；必要时补充例外。
- 同一概念使用同一术语，避免交替称为“收藏”“喜欢”“订阅”。
- 使用熟悉、具体的词，不靠抽象形容词表达要求。
- 区分“必须”“可以”“建议”“待确认”，保留必要条件和事实依据。

**示例**：下面均为教学约定。

> 原句：系统应智能处理各种异常，保证数据一致性并提供良好体验。

> 改写：服务器确认保存失败时，页面保留操作前的已确认状态，并显示失败提示与重试入口。请求超时且结果未知时，页面提示“结果待确认”，重新读取服务器状态后再显示结果。

简明不等于省略机制。若一句话包含多个独立规则，拆开表达；若删除条件会改变结果，就必须保留。

## 从全景组织章节

先写一句话主线，例如：“本文为研发和测试约定个人收藏功能的行为与验收方式。”然后用读者问题确定结构。

| 读者问题 | 章节职责 |
| --- | --- |
| 为什么做、做到哪里？ | 目标、范围、非目标 |
| 特定条件下会发生什么？ | 场景、规则、例外 |
| 怎样实现这些约定？ | 实现设计中的职责、接口与数据约束 |
| 怎样判断完成？ | 验收条件、验证方式与未决事项 |

目录用于组织已经明确的行为，不能替代全景确认。每章应围绕一个职责，避免后面的实现章节另起一套业务规则。

## 用例子帮助判断

先给简短结论，再给一个正常例和一个容易误读的反例。例如“取消收藏只删除收藏关系”：取消后文章仍在全部文章列表中；不能删除文章记录。

多项条件影响同一结果时，用决策表；需要比较操作体验时，用 HTML 演示。首屏突出当前问题，长解释与来源按需展开，完整草稿始终可访问。

给 AI 提供风格样例时，明确“只学习表达，不迁移业务规则、字段或数值”。没有已确认指标时，不凭空补响应时间、并发量或增长率。

## 图表与正文使用同一组规则

| 要解释什么 | 采用什么 | 检查重点 |
| --- | --- | --- |
| 流程和分支 | 流程图 | 条件、结束、失败和返回路径 |
| 对象状态 | 状态图 | 合法变化、触发和失败时状态 |
| 条件组合 | 决策表 | 覆盖、优先级和未定义组合 |
| 系统交互 | 时序图 | 参与者、顺序、成功与失败结果 |
| 选择对操作的影响 | HTML 演示 | 规则依据、预览状态和提交边界 |
| 外观或场景 | 参考图片或生成示意 | 来源和示意标识，不作为事实证据 |

一张图回答一个主要问题。图注说明适用范围和省略项；文字保留关键规则。精确逻辑优先使用可编辑图表，修改规则时同步源稿和实际渲染结果。

## 固定展示约定

在第一次草稿中确定版式，后续沿用。无需每轮生成一套新页面。

| 元素 | 统一约定 |
| --- | --- |
| 标题 | 一级为文档名，二级为主题；同级标题职责与层级一致 |
| 规则 | 编号稳定，条件、动作、结果的顺序一致 |
| 表格 | 同类表格沿用列名和顺序；宽表可横向滚动 |
| 图表 | 使用统一术语、配色和图注；说明适用范围 |
| 状态 | “待确认”“正在修订”“待执行”含义固定，不能只用颜色区分 |
| 网页 | 概览、本轮讨论、全文、记录顺序固定，样式集中复用 |

实际检查桌面与窄屏的阅读顺序、溢出、图中文字和展开操作。样式问题修正后，再核对内容未被裁切或隐藏。文字或表格已经足够时，不为排版增加装饰图。

## 修改与交付检查

修改前记录新决定与影响；修改后检查正文、定义、例子、图表、设计与验收中的旧规则残留。全文检查范围大，实际修改只覆盖必要位置。

交付前检查：

- 核心行为符合明确确认的场景，假设没有变成事实。
- 忽略外部链接后，仍能解释必要定义、条件、结果和例外。
- 同一案例在正文、图表和验收中得到相同结果。
- 全景与详细内容一致，未决问题没有被措辞掩盖。
- 标题、术语、表格、图注和状态展示沿用统一约定。
- 实际渲染已检查；未执行的验收没有标为通过。
