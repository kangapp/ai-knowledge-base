# 阶段检查与记录

在某个阶段需要具体检查项时再使用本页。先看[开始共创](README.md)了解整体流程；下面的记录由 AI 根据实际材料维护，你只处理当前影响最大的一个决定。

需要直接用于对话的指令时，打开[项目 Prompt 工具箱](prompts.md)，按当前阶段展开并复制相应模板。

<h2 id="selection">选型比较与决定记录</h2>

先整理用途、规模、预算、已有技术能力和运行环境，再比较 2–3 个可行方案。AI 查阅候选技术的官方文档，记录适用版本与来源；价格或限制需要实时查证，未核实处保留待定。

AI 推荐方案时说明前提与主要影响，不用没有依据的分数代替判断。最小验证只回答当前未知问题，例如能否在目标环境完成一次数据读写。

决定记录至少包含：**决定内容、依据与适用前提、影响范围、确认状态**。另外维护假设、建议和待定问题；只有明确确认的内容进入已确认决定，待定问题注明它阻塞什么。

<h2 id="coding">编码与验证检查</h2>

把一个小步定义为可以检查的用户行为，例如“保存后刷新仍能看到收藏”。AI 先查相关代码和约束，再完成实现、执行必要检查并更新运行说明。需要复现的缺陷，修复后重跑原复现步骤。

<ul>
<li><strong>需求对应：</strong>本次改动服务哪个规则或验收条件，是否引入了未经确认的新行为？</li>
<li><strong>实现范围：</strong>能否复用已有模式，改动是否限制在相关代码与文档？</li>
<li><strong>必要场景：</strong>正常操作、失败反馈、重复操作和涉及的边界是否得到验证？按实际行为选用，不机械堆积测试。</li>
<li><strong>界面体验：</strong>涉及界面时，在浏览器中检查结果、交互和适用屏幕宽度。</li>
<li><strong>结果记录：</strong>留下执行环境、版本、命令或操作、预期与实际结果；缺工具或环境时标记未验证并说明影响。</li>
</ul>

AI 提供的测试通过记录只能支持实际检查过的范围。若规则本身不清楚，先回来澄清，不通过修改验收口径掩盖实现失败。

<h2 id="release">上线与回滚检查</h2>

发布说明先写清目标环境和版本，再给步骤与验收。已确认的授权继续有效；若目标、数据影响或发布范围发生变化，先说明变化并处理关键取舍。

<ul>
<li><strong>发布目标：</strong>目标环境、入口、版本标识和访问范围已明确，可以判断线上究竟运行哪一版。</li>
<li><strong>配置与数据：</strong>区分代码、配置、密钥与持久数据；说明配置名称和取得方式，文档和仓库不保存真实密钥。</li>
<li><strong>发布步骤：</strong>按实际托管方式记录构建、发布和启动步骤，保留执行结果。</li>
<li><strong>上线验收：</strong>检查目标入口、访问限制和核心用户行为；涉及持久数据时，验证应用重启后数据仍可读取。</li>
<li><strong>失败恢复：</strong>说明什么结果判定发布失败、如何找到上一可用版本、如何恢复及再次验收。</li>
<li><strong>数据变更：</strong>若涉及数据结构迁移，单独核对备份、旧代码兼容性和恢复办法，避免把代码回滚当成数据恢复。</li>
</ul>

部署命令成功只是一个执行结果。目标环境的核心验收通过后，才能将这一版本记录为上线成功；未通过时，先修复或按已确认方案恢复。

<h2 id="operations">运维与变更记录</h2>

运行说明需要让下一次排障有入口。为实际需要覆盖的故障写清发现方式、处理步骤和恢复标准；复杂度根据项目规模和可接受损失决定。

<div class="table-scroll" role="region" aria-label="运行维护说明应记录的内容" tabindex="0">
<table>
<thead><tr><th scope="col">要回答的问题</th><th scope="col">应留下的具体信息</th></tr></thead>
<tbody>
<tr><th scope="row">怎样判断运行正常？</th><td>健康检查入口、核心操作检查方式、检查时机和异常由谁处理；自动化检查需单独配置并验证。</td></tr>
<tr><th scope="row">失败时从哪里查？</th><td>日志入口、时间与错误信息、当前版本和最近变更；以实际证据定位原因。</td></tr>
<tr><th scope="row">怎样恢复数据？</th><td>备份范围、频率、保留时间、存放位置、最近恢复验证结果。根据可接受数据损失选择安排，并验证目标故障发生后备份仍可获取。</td></tr>
<tr><th scope="row">怎样发布下一版？</th><td>变更内容、影响范围、验证结果、目标版本、发布时间和回滚入口。</td></tr>
</tbody>
</table>
</div>

故障处理按“发现异常 → 收集证据 → 确认原因与影响 → 修复或恢复 → 核对核心验收”推进。恢复后同步运行说明和变更记录；新的业务需求回到 Spec，影响架构的约束变化再回到选型。

**一次对话结束不代表监控已经持续运行。** 若需要定时检查，必须实际配置、执行并验证对应任务。备份也需要在隔离环境验证恢复，不能只以备份文件存在作为通过依据。

<h2 id="records">如何记录进展，而不增加阅读负担</h2>

默认每轮只展示本次产物、变化、验证结果和一个需要决定的问题。完整记录留在项目文档中，复用已有目录与文件，不必为了套模板新建一整套管理系统。

```text
当前阶段与目标：
本轮产物及位置：
实际验证：环境 / 版本 / 操作 / 结果
本轮新增的已确认决定：
假设与建议：
待定问题：影响什么 / 是否阻塞
下一步：
```

如果恢复旧版本或修改先前决定，AI 应更新当前记录并保留变更理由，避免后续继续使用失效的约定。
