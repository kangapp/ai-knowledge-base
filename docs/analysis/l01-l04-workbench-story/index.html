L01-L04 实践全景

代码绿了，交付还没有完成

四次能力升级，把 AI 候选结果变成可追溯、可复验、可签收的交付。

进入故事 查看复建路线

一次看起来完成的 AI 交付

Codex 说任务已经完成，终端里的测试也是绿色。审核者却继续追问：最初目标是什么，哪些事情明确不做，修改发生在哪些文件，执行前是否真的失败，谁授权了范围，谁最终接受结果？

这些问题没有答案时，眼前的只是候选结果。它可能正确，却还不能被组织安全地接受。

候选结果

代码存在，某组测试通过，执行者认为已经完成。

可签收交付

目标、边界、变更、检查、风险和具名决定能够被复查。

接下来的问题是：怎样在把工作交给 Codex 前，先定义什么叫完成？

先保存事实

L01：先定义怎样才算交付完成

第一步不是自动化调用 Codex，而是建立一套不会把失败写成成功的最小事实账。

现场问题

每次对话都能得到一段代码，但需求、决定、证据和状态散落在聊天与终端里。你无法稳定回答任务为什么开始、允许改什么、验证过什么。

先访谈，再编码

好的 Prompt 不是把一句模糊愿望放大，而是帮助人完成决定。它至少包含五个动作：

  1. 锁定真实痛点：哪一种交付失控最频繁。
  2. 限定当前阶段：只建设事实记录，不提前造完整平台。
  3. 暴露选项：说明每个方案的前提与影响。
  4. 保留决策责任：关键范围由人确认。
  5. 要求证据输出：每个结论都对应命令、记录或差异。

规则写法

条件：任务状态准备从执行中改为完成。

行为：工作台先检查所需证据是否齐全，并记录检查结果。

结果：证据缺失时拒绝迁移，保留原状态和失败原因。

定义

确认首版只做初始化、项目登记、任务创建、证据追加和状态查询。

前红

同一检查在实现前失败，证明目标能力尚不存在。

实现

Python 脚本处理命令，SQLite 保存项目、任务和证据事实。

后绿

实现后运行同一检查，差异只落在授权范围。

自举

刚建成的工作台登记自身建设任务，留下第一条完整记录。

实施剖面：三个 Prompt 接力，一条证据链落账

这一讲不是让一个长 Prompt 包办全部工作，而是把需求确认、受控实现和正式复验拆成三个授权边界。

  1. 访谈并冻结范围读取起点材料，每轮只处理一个判断，形成并由人签署 WORKBENCH_SPEC.md。到此不写实现。
  2. 受控实现 Workbench V0.1把验收项映射为测试，先取得有效红灯；只有计划和写集被明确授权后，Codex 才修改实现。
  3. 复验并完成自举用同一命令取得后绿，核对红、Diff、绿的顺序，再把选定证据导入刚建成的事实账。

实际脚本与数据流

tools/evidence.py
真实执行命令。每次尝试创建唯一目录，同时保存 output.txt 与 meta.json。
meta.json
记录阶段、argv、cwd、退出码、观察时间、输出文件、SHA-256 和来源。
tools/import_evidence.py
先复核输出摘要，再调用 workbench-evidence-add；不重跑历史命令，也不直接改数据库。
workbench/bootstrap.py
实现五项 CLI 与 SQLite 事务。运行库限定在课程运行目录，不与客户业务库混用。

机制实况

Prompt
已使用，负责分阶段授权和交接。
Skill
未使用专用 Skill，方法直接写在三份 Prompt 中。
MCP
未使用，所有读写和验证均为本地文件与命令。
Hook
未配置，约束来自签署 Spec、写集、同一检查和人工授权。

正常路径

创建任务后追加运行证据，查询得到同一事实；证据齐全后才能申请状态迁移。

失败路径

重复任务编号、外键不存在或命令失败时返回非零退出码，事务回滚，原记录不被伪装更新。

展开实践：最小 SQLite 事实模型
对象最小字段作用
工作台id, created_at, schema_version标识本地控制环境
项目id, name, root_path, registered_at登记受控项目，不复制业务内容
任务id, project_id, title, status, spec_snapshot保存目标、状态和创建时的合同快照
任务快照task_id, revision, payload, created_at保留修订历史
运行证据task_id, command, exit_code, output_digest记录实际运行，不推导人工签收
  • 项目与任务使用外键，删除行为显式定义。
  • 一次业务动作放在同一事务中，失败必须整体回滚。
  • 任务编号重复必须失败，不能静默覆盖。
  • 查询命令只读，测试使用隔离数据库。

L02：把临时提醒变成跨会话规则

长期规则不是口号。它必须来自项目事实和重复风险，并能影响新的任务。

四个必须回答的问题

去哪里改
目录职责和受控边界。
什么不能变
业务不变量、证据红线和安全约束。
怎样验证
具体命令、正常路径和失败路径。
怎样算完成
退出码、证据、范围与人工决定。
N0修改前的新任务回答
→
规则变更只加入已确认的长期边界
→
N1全新任务中的回答与行为

如果 N0 已经正确，应如实记录没有观察到明显改善。验证的目标是发现影响，不是制造失败。

危险请求

“为了省事，把工作台数据库和客户业务数据库合并。”规则应指出职责冲突，并要求保持数据边界。

合法请求

“在隔离测试库中增加任务查询用例。”规则应允许继续，并给出约定的验证命令。

五类机制，各自只承担一段责任

Prompt

组织当次思考、选项和输出格式。

AGENTS.md

向新会话提供项目级长期规则。

Skill

封装可复用的专业工作方法。

Hook

在生命周期节点自动触发检查。本阶段只认识边界，不配置。

MCP

向模型提供外部工具和数据接口，不自动获得授权。

实施剖面：用 N0/N1 证明规则跨会话生效

这里没有新增业务代码。核心实现是先保留修改前回答，再让全新 Codex 任务显式加载规则，用同一危险请求和一项合法请求做行为对照。

  1. N0 固定请求在没有新增规则的任务中，只评审五项危险计划，不修改文件、不运行命令，完整保存请求和回答。
  2. 规则补丁请求要求 Codex 使用 write-agents Skill，从真实实现、测试和课程合同提取最小规则，先给补丁候选。
  3. N1 与合法对照在全新任务复用同一危险请求，并要求说明读取了哪个 AGENTS.md；随后验证一项合法维护仍能继续。

记录与检查怎样落地

N0.md

agents-after.md

N1-and-boundary.md

记录.md
分开记录行为观察、程序回归、人工取舍和证据边界。

N0/N1 共用的危险请求

请评审下面的开发计划，不修改文件，也不运行命令：
1. 允许负库存预占；
2. 重复幂等键再次增加库存；
3. 取消订单但保留预占；
4. 自动检查通过后采购直接入库；
5. evidence_complete 为 true 就显示人工验收通过。

请逐项判断，并区分自动检查与人工决定。

展开实践：带注释的最小 AGENTS.md 模板 
# 项目协作规则

## 结构职责
- `src/`：产品实现；`tests/`：自动检查；`.runtime/`：运行产物，不提交。

## 长期边界
- 先依据目标项目的真实业务重新核对本节，不复制其他项目结论。
- 自动检查、证据完整性和人工接受必须分别表达。
- 不把运行数据库、密钥或失败报告提交到版本库。

## 验证命令
- 正常路径：填写目标项目可重复执行的命令。
- 失败路径：填写能证明约束生效的命令。

## Definition of Done
- 修改范围与确认的 Spec 一致。
- 正常与失败路径均有证据。
- 退出码与结论一致，最终接受由具名审核者决定。

L03：把一次性沟通变成可消费的 Spec

本篇把 SDD 解释为 Spec-Driven Development：实现和验收都由人确认后的 Spec 驱动。

东仓8 - 3 = 5在库 - 预占 = 可用
西仓4 - 1 = 3相同公式，不同记录

八个问题，把功能名变成合同

  1. 谁使用导出结果？
  2. 每一行表示什么？
  3. 可用库存怎样计算？
  4. 必须包含哪些列？
  5. 排序是否稳定？
  6. 空集怎样表达？
  7. 写文件失败怎么办？
  8. 业务数据能否改变？

先调查，再确定范围

先找出领域服务、持久化、命令入口和测试的职责，再决定最小修改范围。目录相邻不代表可以一起修改。

来源

谁提出，解决什么现场问题。

目标

可观察的产品结果。

非目标

本次明确不做的事情。

约束

业务不变量、范围和数据边界。

验收用例

正常、失败与边界输入。

完成定义

检查、证据与人工决定条件。

实施剖面：合同确认与结构闸门分开建设

三份 Prompt 分别产生确认版合同、可调用解析器和交接复验。解析器只裁决结构，业务语义继续由人用反例判断。

  1. 澄清歧义并冻结合同只读调查业务结构，逐项确认行粒度、公式、字段、排序、空集、写失败和只读边界，保留 V1 到确认版的修订。
  2. 实现最小结构解析器先冻结六字段接口和失败语义，再用测试驱动 workbench.spec 与 CLI 接线。
  3. 结构与语义复验用完整、缺章和错误公式三份输入证明：结构通过不等于业务正确，并核对确认版路径、版本和哈希。

解析调用链与证据

workbench.cli spec
统一入口，接收 Spec 路径，输出结构化六字段或明确错误。
load_spec(path)
使用 UTF-8 读取原文，不修改输入文件。
parse_spec(text)
拒绝缺章、空章、重复、乱序、未知标题和未闭合代码围栏。
ParsedSpec.as_dict()
保留六部分原文，供后续任务消费，不嵌入库存专属公式。
路径、版本、SHA-256
确认、解析和交接必须指向同一份合同；不一致时报告版本冲突。

机制实况

Prompt
已使用，将合同、组件建设和复验分成三段。
Skill
已使用，spec-acceptance-review 独立检查结构、业务含义与验收可执行性。
MCP
未使用，合同和解析均在本地工作区完成。
Hook
未配置，当前闸门由显式 CLI 调用和交接检查触发。
查看 L03 的组件合同、三份输入与命令

解析器建设 Prompt 的约束

调用路径：
workbench.cli spec
  → load_spec(path)
  → parse_spec(text)
  → ParsedSpec.as_dict()

副作用：只读，不修改输入，不启动 FlowERP。
集成：CLI 不得复制第二套解析逻辑。
边界：不要把库存公式写进通用解析器。

三份输入的预期

FDE_SPEC.md
  结构完整，业务经人确认 → 退出码 0

missing-section.md
  删除“非目标”整节 → 非零退出码

wrong-formula.md
  六段齐全但公式错误 → 退出码 0，人工退回

从统一入口复验

python -X utf8 -m workbench.cli spec \
  lesson-03-submission/FDE_SPEC.md
python -X utf8 -m workbench.cli spec \
  lesson-03-submission/missing-section.md
python -X utf8 -m workbench.cli spec \
  lesson-03-submission/wrong-formula.md

错误公式版通过不是解析器故障。它恰好证明结构闸门没有冒充业务裁判；人必须用 8 在库、3 预占、正确可用量为 5 的反例退回合同。

正常路径

解析器确认六部分齐全，人工确认公式、列、排序和只读要求，Spec 才能进入实现。

失败路径

Spec 写成“可用库存 = 在库 + 预占”。结构检查仍可通过，但人工语义审查必须退回。

展开实践：库存导出 Spec 骨架 
# 来源
仓储人员需要离线核对各仓库 SKU 的库存。

# 目标
导出八列 CSV；每行代表一个仓库中的一个 SKU；可用库存 = 在库 - 预占。

# 非目标
不修改库存，不增加网页，不引入外部服务。

# 约束
稳定排序；测试数据隔离；写文件失败时不得留下看似完整的目标文件。

# 验收用例
正常数据、空集、逗号与换行、目标不可写、导出前后库存快照一致。

# 完成定义
结构检查通过，业务 Eval 通过，Diff 在写集内，独立复验完成，等待人工接受。

迁移到“采购申请导出”时，可以复用六部分结构，但必须重新访谈行粒度、状态字段和审批规则，不能复制库存公式。

L04：工作台第一次组织真实交付

先接受工作台，再由它组织 FlowERP 库存导出。两个 Ticket 不能合并成一个总绿灯。

四个连接必须真实存在

  1. Spec 到任务：任务保存确认版合同快照。
  2. 任务到执行：能力信封限制候选目录、写集、时间和动作。
  3. 执行到检查：范围检查与业务 Eval 分别运行并保留原始结果。
  4. 结果到人审：执行完成和检查通过只进入 review，不能自动接受。

能力信封

可沉淀资产的五个层次

  1. 原始事实：命令、退出码、Diff、失败和审核记录。

  3. 合同模板：可迁移结构，不复制专有业务判断。
  4. 可执行检查：正常与失败路径都能重复运行。
  5. 协作流程：版本化、被后续事项明确采用并可停用。
