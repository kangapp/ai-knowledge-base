# 文件与记录管理指南

## 信息流转总原则

同一信息只在最合适的位置成为事实源：术语进入 `CONTEXT.md`，长期技术取舍进入 ADR，需求行为进入 Spec，实施范围进入 Ticket，执行细节进入代码和测试。下游引用上游，不复制整份内容。

## 长期项目配置

### `AGENTS.md`

- **记录目的**：全项目必须遵守的协作与编码规则。
- **内容**：项目边界、常用命令、硬规则、文档路由、Skills 配置入口。
- **维护**：规则变化时由维护者更新；所有工程 Skill 读取。
- **版本管理**：提交 Git，长期保留。
- **不应记录**：单个功能的临时需求或当前会话进度。

### `docs/agents/*.md`

| 文件 | 记录逻辑 | 主要消费者 |
| --- | --- | --- |
| `issue-tracker.md` | 事项放在哪里、如何创建/读取/关闭、依赖关系如何表示 | `triage`、`wayfinder`、`to-spec`、`to-tickets`、`code-review` |
| `triage-labels.md` | 五类规范角色到实际标签字符串的映射 | `triage`、创建 Agent-ready 工作的 Skill |
| `domain.md` | 术语表和 ADR 的位置及读取规则 | 领域、设计、实现、测试、诊断类 Skill |

这些文件由 Setup 创建，工作方式改变时更新；都提交 Git。

## 长期领域知识

### `CONTEXT.md`：项目术语表

- **记录什么**：领域概念、精确定义、概念关系、明确排除的同义说法。
- **谁维护**：`domain-modeling`；`grill-with-docs` 和架构讨论在术语确定时触发更新。
- **谁读取**：需求、实现、测试、诊断和审查流程。
- **生命周期**：按需创建，长期修订并提交 Git。

正确示例：

```markdown
## 收藏文章

用户明确标记为值得后续查看的文章。

“收藏”只表示阅读意图，不表示文章通过质量审核。
```

错误示例：

```markdown
收藏状态存放在 articles.is_favorite 字段。
```

这是实现细节，应留在 Spec、Ticket、代码或必要的 ADR 中。

### `docs/adr/NNNN-*.md`：技术决策记录

只有同时满足以下三点才创建：改变代价较大、没有上下文会令人意外、确实比较过不同方案。

最小结构：

```markdown
# ADR-0001：收藏状态保存在 SQLite

## 背景
收藏需要在静态站重新构建后仍然存在。

## 决定
在现有 SQLite 中保存收藏状态。

## 备选方案
- 只保存在浏览器 localStorage
- 新建独立数据服务

## 后果
收藏可被 API 和构建器统一读取，但需要数据模型变更。
```

ADR 提交 Git，原则上不静默改写历史决定；决定失效时新增 ADR 说明替代关系。

## GitHub 事项记录

### Spec Issue：需求说明

记录目标、用户行为、范围、不做什么、验收标准和已确认测试切入点。它回答“最终要做成什么”，不规定每个函数如何写。

### Ticket Issue：实施任务

记录一个可独立验证的纵向切片、验收标准、前置阻塞和来源 Spec。完成后关闭，不把后续无关需求不断追加到旧 Ticket。

### Agent Brief：AI 执行说明

写在需要交给新会话的 Issue 评论中，包含背景、相关模块、约束、验收标准和验证命令。它引用 Spec 与 ADR，不复制全部历史讨论。

## 阶段性或临时产物

| 产物 | 保存位置 | 记录内容 | 是否提交 |
| --- | --- | --- | --- |
| Research Markdown | 仓库已有研究目录 | 一手资料、引用、结论和未知项 | 是 |
| Prototype branch | 独立临时分支 | 可运行验证代码、问题与结论 | 不合入主分支 |
| Architecture report | 操作系统临时目录 | 架构候选与证据 | 否 |
| Handoff Markdown | 操作系统临时目录 | 当前状态、下一目标、正式产物指针 | 否 |
| Tests | 项目测试目录 | 通过公开接口表达的行为契约 | 是 |
| Code Review report | 当前审查会话或 PR | 规范轴与需求轴结论 | 视团队流程 |

## 本项目不使用的替代方案

`.scratch/<feature>/issues/` 是没有远程事项系统时的本地 Markdown Tracker。本项目已经选择 GitHub Issues，因此不要同时维护 `.scratch/` 副本。

## 更新与清理检查表

1. 这是术语、长期决定、需求、任务还是实现证据？
2. 是否已有事实源可以引用，而不是再复制一份？
3. 新会话能否只靠 Ticket、项目规则和引用文件正确开始？
4. 临时原型、报告和 Handoff 是否误入主分支？
5. 已关闭任务是否仍被当成活跃计划继续追加？
