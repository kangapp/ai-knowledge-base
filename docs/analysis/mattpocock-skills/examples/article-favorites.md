# 贯穿案例：文章收藏功能

这是一个教学示例，用来展示信息如何从想法流入术语、技术决策、需求说明、实施任务、测试和提交；下文的需求和回答为示例设定，不表示项目已经实现这些功能。

## 1. 模糊想法

> 我想把值得以后阅读的文章标记起来。

`grill-with-docs` 先读取项目已有边界，已明确的单用户约定不再问一遍。第一轮把前提已满足的决策一起提出：

| 第一轮问题 | 建议与示例回答 |
| --- | --- |
| 收藏是否影响审核状态？ | 建议只表达阅读意图；示例回答：不影响 |
| 一期需要分类吗？ | 建议先不分类；示例回答：只要收藏与筛选 |
| 状态只在当前浏览器可见，还是所有访问设备一致？ | 先确认保存语义；示例回答：同一服务的数据在各设备一致 |

跨设备一致确定后，第二轮再讨论持久化方案和状态读取时机。用户确认共享理解后，流程继续。若这些条件已经在对话中明确，就直接复用；分轮的价值在于遵守问题依赖。[grilling 定义](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/productivity/grilling/SKILL.md)

## 2. 项目术语表

`CONTEXT.md` 只记录稳定领域含义：

```markdown
## 收藏文章

用户明确标记为值得后续查看的文章。

收藏表示阅读意图，不表示文章通过质量审核。
```

## 3. 技术决策记录

如果浏览器本地存储和 SQLite 持久化之间存在真实且长期的取舍，可以创建 ADR。若实现选择很普通、容易改变，就不创建 ADR，避免文档泛滥。

如果“取消收藏后应当立即从筛选列表消失，还是保留到刷新”必须操作后才能判断，可以先做可双击打开的逻辑 HTML：显示收藏集合、当前筛选状态，提供收藏/取消按钮和场景演练。用户确定行为后，演示提交到 `prototype/article-favorites` 证据分支，并从事项单引用；可验证的纯逻辑按需要提取。这个清晰的小功能通常无需 Wayfinder 地图。

## 4. Spec Issue

```markdown
# 支持收藏和筛选文章

## 目标
用户可以保存值得后续阅读的文章，并从文章列表筛选收藏内容。

## 范围
- 收藏文章
- 取消收藏
- 筛选已收藏文章

## 不在范围
- 多用户
- 收藏夹分类
- 实时同步

## 测试决策
- 用已确认的 API 接口验证收藏、取消与持久化
- 用浏览器交互检查按钮、列表筛选和刷新后的显示
- 预期结果来自这里的行为定义，不复制实现算法

## 验收标准
- 收藏后刷新页面，状态仍然存在
- 可以只查看收藏文章
- 取消收藏后从收藏筛选结果中消失
```

## 5. Ticket Issues

推荐按可用行为拆分：

1. 用户可以收藏和取消收藏文章。
2. 用户可以筛选已收藏文章，前置依赖任务 1。

每张任务包含所需的数据、API、页面和验证改动。远程 Tracker 中先创建任务再连接依赖，任务 2 必须等任务 1 完成。若项目选择本地 Tracker，同样内容分别写入 `issues/01-toggle-favorite.md` 与 `issues/02-filter-favorites.md`。

实施时每票开启干净会话，从任务正文和引用恢复上下文；这些已经就绪的任务不再交给 `triage`。

## 6. Agent Brief

外部请求经 `triage` 交接时会生成 Agent Brief。本例的任务由 `to-tickets` 生成，可以直接在任务中保留下面这些必要执行信息，无需再复制一条同内容的评论：

```markdown
目标：实现事项单中的收藏/取消收藏行为。

约束：
- 不引入用户系统
- 数据库操作通过 src/db/operations.py
- API 使用统一响应信封

验收：
- 收藏状态可以持久化
- 重复收藏结果稳定
- 取消收藏后状态消失

验证：
uv run pytest tests/test_api_contracts.py
```

## 7. TDD 与实现

先确认 API 和浏览器交互是这项功能的测试切入点，再逐条执行。以下仅展开 API 的两个切片：

```text
收藏请求的失败测试
→ 最小数据库和 API 实现
→ 测试转绿
→ 取消收藏的失败测试
→ 最小实现
→ 测试转绿
```

页面切片继续验证收藏按钮和筛选后的可见结果。每轮只做一个失败测试所需的实现；类型检查和定向测试及时运行，结束时执行完整测试套件。当前上游把重构放在审查阶段。

## 8. Code Review 与提交

规范轴检查数据库访问、响应信封、依赖和文档写回规则，并把代码气味作为判断提示；需求轴检查收藏、取消和持久化是否符合 Spec，有没有擅自加入分类或多用户功能。两个审查子任务的结果分别报告。审查前核实比较范围包含本轮实际改动，尤其是尚未提交的文件。

提交信息引用 Ticket，让后续审查可以找到需求事实源。Ticket 验收完成后关闭。

## 最终信息链

```text
CONTEXT.md：收藏到底是什么
ADR：为什么采用某个长期存储方案（只有需要时）
Spec Issue：完整功能要达到什么结果
Ticket Issues：每个会话交付哪项行为
Agent Brief：新会话如何正确开始
Tests：行为如何被自动验证
Code + Commit：最终实现和可追溯变更
```

如果过程中只是需要继续同一项工作且空间充足，就继续当前会话；只有切换工具、目录或协作者等需要携带上下文的情况才生成 Handoff。案例采用的当前路线和阶段边界见 [ask-matt](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/ask-matt/SKILL.md)，核对日期 2026-09-13。
