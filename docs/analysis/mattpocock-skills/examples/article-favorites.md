# 贯穿案例：文章收藏功能

这个案例展示信息如何从想法流入术语、技术决策、需求说明、实施任务、测试和提交。

## 1. 模糊想法

> 我想把值得以后阅读的文章标记起来。

`grill-with-docs` 会确认“收藏”是否等于审核通过、是否需要分类、是否跨设备保存、是否属于多用户能力。根据本项目边界，确定一期只支持单用户收藏与筛选。

## 2. 项目术语表

`CONTEXT.md` 只记录稳定领域含义：

```markdown
## 收藏文章

用户明确标记为值得后续查看的文章。

收藏表示阅读意图，不表示文章通过质量审核。
```

## 3. 技术决策记录

如果浏览器本地存储和 SQLite 持久化之间存在真实且长期的取舍，可以创建 ADR。若实现选择很普通、容易改变，就不创建 ADR，避免文档泛滥。

## 4. Spec Issue

```markdown
# 支持收藏和筛选文章

## 目标
用户可以保存值得后续阅读的文章，并从文章列表筛选收藏内容。

## 范围
- 收藏文章
- 取消收藏
- 筛选已收藏文章

## 不在范围
- 多用户
- 收藏夹分类
- 实时同步

## 验收标准
- 收藏后刷新页面，状态仍然存在
- 可以只查看收藏文章
- 取消收藏后从收藏筛选结果中消失
```

## 5. Ticket Issues

推荐按可用行为拆分：

1. 用户可以收藏和取消收藏文章。
2. 用户可以筛选已收藏文章，前置依赖任务 1。

不要拆成“改数据库、改 API、改页面、写测试”，因为每张水平任务都不能独立交付用户行为。

## 6. Agent Brief

```markdown
目标：实现事项单中的收藏/取消收藏行为。

约束：
- 不引入用户系统
- 数据库操作通过 src/db/operations.py
- API 使用统一响应信封

验收：
- 收藏状态可以持久化
- 重复收藏结果稳定
- 取消收藏后状态消失

验证：
uv run pytest tests/test_api_contracts.py
```

## 7. TDD 与实现

先确认 API 是测试切入点，再逐条执行：

```text
收藏请求的失败测试
→ 最小数据库和 API 实现
→ 测试转绿
→ 取消收藏的失败测试
→ 最小实现
→ 测试转绿
```

## 8. Code Review 与提交

规范轴检查数据库访问、响应信封、依赖和文档写回规则；需求轴检查收藏、取消和持久化是否符合 Spec，有没有擅自加入分类或多用户功能。

提交信息引用 Ticket，让后续审查可以找到需求事实源。Ticket 验收完成后关闭。

## 最终信息链

```text
CONTEXT.md：收藏到底是什么
ADR：为什么采用某个长期存储方案（只有需要时）
Spec Issue：完整功能要达到什么结果
Ticket Issues：每个会话交付哪项行为
Agent Brief：新会话如何正确开始
Tests：行为如何被自动验证
Code + Commit：最终实现和可追溯变更
```
